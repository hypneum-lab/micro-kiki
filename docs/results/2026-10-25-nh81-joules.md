# NH-81 result: measured joules per token, spiking vs dense (macM1)

**Preregistration:** `docs/prereg/2026-10-25-nh81-joules-per-token.md`
(tag `prereg-nh81-20261025`, pushed before any measurement) and
`docs/prereg/2026-10-28-nh81-amendment-1.md`.
**Issue:** #14. **Measured:** 2026-10-25 21:28-22:27 CET, macM1 (M1 Max),
MLX 0.31.1 on Metal, fp32, GPU rail via IOReport (amendment A1).
**Artifacts:** `results/nh81/` (`measure.jsonl` raw windows,
`summary.json` statistics, `selection.json`, `train-*/` logs and configs).

## Verdict

**Withdraw the energy argument definitively for GPU/M1-class hardware.**
Primary block (W1 generation, fused spiking path, GPU rail):
**R-hat = 0.91, 95 % CI [0.83, 1.01]**, 12/12 valid pairs, iso-quality met.
R-hat <= 1.1 is the preregistered "withdraw" condition; the catalogue
reading is "NH-81 supported". Every secondary block points the same way.

R = (J/token dense) / (J/token spiking); R < 1 means the spiking model
uses more energy.

## Model pair and iso-quality

BSK architecture (D=384, L=6, SEQ=128, 26.5 M parameters), dense `ann1`
vs spiking `spkt` (signed rate-LIF FFN, T=6, firing-rate L1 0.2), same
French Gutenberg corpus (11.8 M train tokens), 12 000 steps each.

| | test loss (nats/token) | val loss |
|---|---|---|
| spiking, step 12 000 | 3.6445 | 3.5882 |
| dense D*, step 12 000 (closest val) | 3.6372 | 3.5884 |
| gap (spiking - dense) | **+0.007** (margin 0.02) | |

The training curves are almost superposed. At this scale and with ANN
attention, the rate-coded FFN costs no measurable quality, unlike the
0.23-0.34 nats reported for fully spiking RWKV models at equal FLOPs
(arXiv:2610.15146). Measured test firing: **13.8 %** of neuron-ticks,
not the 1-3 % quoted in the BSK README.

## Energy (GPU rail, net of rest power; mean over valid pairs)

| block | pairs | dense mJ/token | spiking mJ/token | R-hat [95 % CI] | dense tok/s | spiking tok/s | decision |
|---|---|---|---|---|---|---|---|
| **W1 gen, fused (primary)** | 12/12 | 41.3 | 45.5 | **0.91 [0.83, 1.01]** | 447 | 278 | withdraw |
| W1 gen, event | 12/12 | 40.0 | 84.0 | 0.48 [0.47, 0.48] | 452 | 162 | withdraw |
| W2 scoring, fused | 12/12 | 0.296 | 0.404 | 0.73 [0.73, 0.74] | 159 k | 73 k | withdraw |
| W2 scoring, event | 12/12 | 0.296 | 0.651 | 0.45 [0.45, 0.46] | 159 k | 52 k | withdraw |

Mean GPU power during runs: W1 dense 18.4 W vs spiking 12.9 W (fused);
W2 dense 47.2 W vs spiking 29.5 W (fused). The spiking model draws less
power but runs longer: the LIF loop (2 populations x 6 ticks of
element-wise work per FFN) lowers throughput by 38 % (W1) to 54 % (W2),
and the energy per token ends up equal or higher. In W1 at batch 1 the
GPU is partly idle per token, which is why the fused path comes close to
parity (and why its CI is wider); in the compute-bound W2 the penalty is
clear. The event formulation (one `down` matmul per tick) roughly doubles
the cost, as expected from dense kernels on binary inputs.

Analytical memory traffic (not measured): both models read 106 MB of fp32
weights per forward. Without fusion, the spiking FFN adds about 47 MB of
LIF state traffic per layer per 128-token window (2 x 6 ticks x about
5 tensor accesses x 0.79 MB), about 2.7x the weight traffic. `mx.compile`
fuses part of it. Spike sparsity cannot be exploited by these kernels.

## Background noise

* Run rest windows (52 x 20 s, models loaded, nothing running): GPU rail
  **1.7 mW** mean (max 15 mW), i.e. < 0.01 % of run power; background GPU
  utilisation 2.4 % mean (max of window means 2.8 %, threshold 10 %); no
  other Python process > 20 % CPU in any rest window; OrbStack (VM `srv`)
  9.7 % CPU mean, 58.5 % max. No pair was rejected.
* Probe of 2026-10-28 15:24 (60 s, read-only, no model loaded):
  GPU rail 0.41 W, GPU utilisation 19 % mean (max 70 %) from other
  sessions' jobs (dream-of-kiki, bouba_sens; load average 34), OrbStack
  8.7 % CPU, second-brain workers (STT :9422, embed :9423, rerank :9424,
  :8080, :9311) idle at about 0 % CPU. A run under these conditions would
  have been refused by the start guard; the 2026-10-25 run took place in a
  clean window.
* The CPU rail could not be read (IOReport CPU channel frozen,
  amendment A2); CPU stays descriptive-only per the preregistration and is
  not reported.

## Limits

One pair at 26.5 M parameters, one seed, fp32, one GPU (M1 Max), dense
kernels only. The result is about GPU/M1-class execution, not about
neuromorphic silicon, where spike sparsity can be exploited. Instrument:
IOReport GPU rail without a powermetrics cross-check (amendment A1).
