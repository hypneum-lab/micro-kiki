# Demo: Qwen3.6-35B-A3B BF16 + micro-kiki LoRA adapters on one GB300 GPU, with J/token

**This is a demo, not a scientific claim.** It tests no hypothesis,
feeds no Hypneum verdict, and its numbers are not evidence about the
adapters' quality or about routing. It is pre-registered (descriptive
protocol) so that what is run, on which weights and prompts, and how
energy is read, is fixed before the slot.

**Level:** L0 (draft on a branch, not frozen). L1 requires every
"TBD by PI" item closed, the harness of section 7 committed and
reviewed, the package list reviewed, the PR merged on green CI, an

**Date:** 2026-10-31.

**Depends on:** the NH-81 GB300 pre-registration
(`docs/prereg/nh81-gb300/`, separate PR): same host, same NVML

## 1. What is shown

One GPU serves the BF16 base and switches between per-domain LoRA
adapters; for each domain, the same frozen prompts are answered by the
base model and by the base + that domain's adapter, and the energy per
generated token is read with the NH-81 NVML instrument. Output: a table
of J/token, tokens/s and the generated texts, per domain and arm.

## 4. Protocol

* **Host and GPU:** the GB300 handle chosen by PCI bus ID, UUID passed
  to `CUDA_VISIBLE_DEVICES`, UUID check before the first run; host
  record as in the NH-81 GB300 prereg, section 2. Nothing else runs on
  the GPU or heavily on the CPU during the demo window.
* **Arms:** `base` (no LoRA) and `adapter:<domain>`.
* **Run:** the 3 prompts of one domain, in file order, batch 1, greedy
  (temperature 0), `max_new_tokens` 256 per prompt, stop at EOS or the
  limit. Prefill is inside the run window.
* **Pair:** 20-s rest window + `base` run + `adapter:<domain>` run, the
  order alternating between successive pairs (B-A, A-B, ...), counted
  over valid pairs; a 20-s rest window after the last pair.
* **Repetitions:** 3 valid pairs per domain (item 2); domains in the
  order of `prompts.json`; at most 6 attempts per domain.
* **Warm-up (unmeasured):** before the first pair, one run per arm of
  the first domain with the first prompt and 16 new tokens.
* **Adapter switching:** one model instance gets the LoRA layers once
  (`linear_to_lora_layers` with the adapter's rank 16, scale 20.0 and
  32 layers); each domain's tensors are loaded into it with
  `load_weights` before its pairs; the switch time is logged and is
  outside every measured window. The `base` arm uses a second instance
  without LoRA layers (item 4). Pre-declared fallback if two instances
  do not fit or fail: per domain, all `base` runs then all adapter runs
  in one block, labelled "sequential".
* **Energy and J/token:** NH-81 instrument (NVML energy counter on the
  GB300 handle, or the pre-declared power-integrated fallback), net
  energy = run energy minus (mean power of the preceding rest window)
  x run duration; J/token = net energy / generated tokens; gross
  J/token and J per (prompt + generated) token also reported.
* **Rest guard:** the NH-81 GB300 rule (T = k x P_rest, same k as the
  NH-81 prereg) with P0 / P_rest / P_load measured again for this
  process (35B model loaded, unmeasured base run as the load). A pair
  is rejected and replayed if a rest window exceeds T, a foreign GPU
  compute process appears, or another Python process exceeds 20 % CPU
  over a window.
* **Statistics:** none inferential. Per domain and arm: median and
  range over the valid pairs; per pair the ratio adapter / base of
  J/token is listed. No CI, no test, no claim of difference.

## 5. Runtime

* MLX `0.31.1` with `mlx-cuda-12==0.31.1` (fallback `mlx-cuda-13`, as
  in NH-81 item 4) and `mlx-lm==0.31.2` (item 3). Checked in the
  `mlx-lm` 0.31.2 wheel (SHA-256
  `a90a7905031b2580b4923f92e0fb156ca287f452bb1a9e41a60dcbc971532d46`,
  read only): `models/qwen3_5_moe.py` loads the Hugging Face BF16
  checkpoint and splits the fused `mlp.experts.gate_up_proj` into
  `switch_mlp.{gate,up}_proj`, with keys renamed to
  `language_model.model.layers.N...`, the naming used by the adapters;
  `tuner/utils.py` wraps `SwitchLinear` in `LoRASwitchLinear`;
  `models/gated_delta.py` uses a Metal kernel on Apple GPUs and a pure
  `mlx` ops path otherwise (expected on CUDA; slower, not measured).
* `mlx-lm` 0.31.2 requires `transformers>=5.0.0`, `sentencepiece`,
  `protobuf`, `pyyaml`, `jinja2`, `numpy`: all go through the HITL
  package review (section 8). No lockfile before that review.
* Memory: about 72 GB per BF16 instance plus about 4.1 GB per float32
  adapter; two instances fit in the 252 GB HBM on paper. The MLX CUDA
  allocator's placement on this coherent CPU-GPU system is not
  verified; peak memory is logged.

## 6. Adapter format and conversion risk (checked 2026-10-31, nothing converted)

**Format found.** Each adapter is an `mlx_lm.lora` output (Hub tags
`mlx`, `mlx-lm`, `library_name: mlx`): `adapters.safetensors` with
816 float32 tensors, no metadata, 4 103 288 730 bytes for 32-layer
adapters (layers 8-39; 2 564 555 362 bytes for the 20-layer ones), and
an `adapter_config.json` (`fine_tune_type: lora`, rank 16, scale 20.0,
alpha 16.0 recorded but unused by mlx-lm, dropout 0, `num_layers` 32,
`model: models/Qwen3.6-35B-A3B`). Key names follow mlx-lm:
`language_model.model.layers.N.<module>.lora_a` / `.lora_b`, with MLX
layouts: `lora_a` is `[in, r]`, `lora_b` is `[r, out]` for linear
modules (e.g. `self_attn.q_proj.lora_a [2048, 16]`,
`lora_b [16, 8192]`), and per-expert stacks for the MoE experts:
`mlp.switch_mlp.gate_proj.lora_a [256, 16, 2048]`,
`lora_b [256, 512, 16]`. Covered modules: `linear_attn.in_proj_{a,b,qkv,z}`,
`linear_attn.out_proj` (24 linear-attention layers), `self_attn.{q,k,v,o}_proj`
(8 full-attention layers), `mlp.gate`, `mlp.shared_expert_gate`,
`mlp.shared_expert.{gate,up,down}_proj`, `mlp.switch_mlp.{gate,up,down}_proj`.
The MLX path of section 5 loads this format as is: **no conversion
for the demo.**

**What a torch / CUDA conversion would require (risk, not done):**

1. Key mapping from `language_model.model.layers.N` to the Hugging Face
   naming `model.language_model.layers.N` (plus the PEFT prefix).
2. Transposition: PEFT `lora_A.weight` is `[r, in]` and `lora_B.weight`
   `[out, r]`, the transpose of the MLX tensors.
3. Scaling: mlx-lm applies `scale` = 20.0 directly; PEFT applies
   `lora_alpha / r`, so `lora_alpha` = 320 for r = 16 (the recorded
   alpha 16 would give scale 1, a silent 20x error).
4. MoE experts: the Hugging Face checkpoint stores experts as fused 3-D
   parameters (`mlp.experts.gate_up_proj`, `mlp.experts.down_proj`), not
   as `nn.Linear` modules. The per-expert gate and up LoRA pairs must be
   combined into one LoRA on the fused `gate_up_proj` (block structure
   of rank 32), and PEFT or vLLM support for LoRA on these fused expert
   parameters of this architecture is not verified.
5. Alternative: merge each adapter into the base (W + 20 x B A per
   module) and save one BF16 model per domain (about 72 GB each, no hot
   swap, a BF16 rounding of the merged weights that is not
   characterised).
6. Each step needs a numerical equivalence test against the MLX output
   (same prompt, logits within a stated tolerance) before any demo use.

**Other risks.** The MLX CUDA backend on `sm_103` and the 64 KB page
size are untested (the NH-81 smoke test runs first); the gated-delta
ops path may be slow on CUDA; the base revision used in training is not
recorded (item 6); the fork-versus-PyPI `mlx-lm` difference may change
numerics (item 3).

## 9. Output format

`results/demo-35b-gb300/`:

* `host.json`: host record, GPU identity (PCI bus ID, UUID), driver,
  CUDA, package versions, sha256 of every loaded file.
* `rest_threshold.json`: P0, P_rest, P_load, k, T.
* `runs.jsonl`, one line per run: `pair`, `attempt`, `domain`, `arm`,
  `order` (`BA` / `AB`), `t_start`, `t_end`, `prompt_ids`,
  `prompt_sha256`, `prefill_tokens`, `generated_tokens`,
  `stop_reasons`, `energy_j` (gross), `rest_power_w`, `net_energy_j`,
  `j_per_token`, `j_per_token_gross`, `tokens_per_s`, `instrument`
  (`nvml_energy_counter` / `power_integrated`), `valid`,
  `reject_reason`, `layout` (`two_instances` / `sequential`).
* `outputs.jsonl`: `domain`, `arm`, `pair`, `prompt_id`, `text`,
  `text_sha256` (item 7 decides whether it is committed).
* `summary.json` and the note `docs/results/2026-11-01-demo-35b-gb300.md`,
  which starts with "Demo, not a scientific claim".
