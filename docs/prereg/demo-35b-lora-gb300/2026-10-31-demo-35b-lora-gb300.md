# Demo: Qwen3.6-35B-A3B BF16 + micro-kiki LoRA adapters on one GB300 GPU, with J/token

**This is a demo, not a scientific claim.** It tests no hypothesis,
feeds no Hypneum verdict, and its numbers are not evidence about the
adapters' quality or about routing. It is pre-registered (descriptive
protocol) so that what is run, on which weights and prompts, and how
energy is read, is fixed before the slot.

**Level:** L0 (draft on a branch, not frozen). L1 requires the PI
decisions below (recorded 2026-10-31), the harness of section 7

annotated tag and a Software Heritage revision SWHID.

## 1. What is shown

One GPU serves the BF16 base and switches between per-domain LoRA
adapters; for each domain, the same frozen prompts are answered by the
base model and by the base + that domain's adapter, and the energy per
generated token is read with the NH-81 NVML instrument. Output: a table
of J/token, tokens/s and the generated texts, per domain and arm.

## 4. Protocol

* **Host and GPU:** the GB300 handle chosen by PCI bus ID, UUID passed
  to `CUDA_VISIBLE_DEVICES`, UUID check before the first run; host
  record as in the NH-81 GB300 prereg, section 2. Nothing else runs on
  the GPU or heavily on the CPU during the demo window.
* **Arms:** `base` (no LoRA) and `adapter:<domain>`.
* **Generation:** batch 1, greedy (temperature 0), `max_new_tokens` 256
  per prompt, stop at EOS or the limit; prompt cache / KV cache reset
  before each prompt; prefill is inside the run window.
* **Run:** the 3 prompts of one domain, in file order, repeated K times;
  K is the smallest value giving >= 15 s (PI decision 11), calibrated on the
  `base` arm of each domain during that domain's unmeasured warm-up and
  used for both arms of that domain. A measured run shorter than 15 s
  is kept, flagged `short` and reported separately; under the
  power-integrated fallback it is also labelled not interpretable.
  Window boundaries are taken after `mx.eval` / device
  synchronisation; with the counter no lag correction is applied, with
  the fallback the 1-s averaging lag is stated as a limitation.
* **Order:** domains in the order of `prompts.json`, all `base`
  blocks first, then all adapter blocks (layout below).
* **Warm-up (unmeasured):** before each (domain, arm) block, one run of
  the domain's first prompt with 16 new tokens.
* **Adapter loading and switching (checked, not trusted):** the
  adapted instance gets the LoRA layers once (`linear_to_lora_layers`
  with rank 16, scale 20.0 and the `num_layers` of the domain's
  `adapter_config.json`; all default domains have 32). Before loading
  a domain, its tensor names, shapes and dtypes are compared with the
  expected list (816 tensors for a 32-layer adapter, names and shapes
  as in section 6); any missing, extra or mis-shaped tensor stops the
  demo. The tensors are then loaded with `load_weights(strict=False)`
  (the default strict mode would also require the base weights) and
  forced with `mx.eval` before any measurement. A switch test runs
  once before the first adapter block: logits of the first prompt on adapter A,
  then B, then A again must be bitwise identical for the two A loads.
* **Layout (PI decision 4): sequential, one instance.** All `base` runs
  of all domains are done first, on the unwrapped model; then the LoRA
  layers are added once and each domain's adapter is checked, loaded
  and run. Each run is preceded by a 20-s rest window, the rest after a
  run being the rest before the next run of the same (domain, arm);
  same guard and replay rules; 3 valid runs per (domain, arm), at most
  6 attempts each. Runs are not paired: per (domain, arm) the median and
  range of J/token are reported, and the ratio of the two medians is
  listed, descriptive only.
* **Energy and J/token:** NH-81 instrument (NVML energy counter on the
  GB300 handle, or the pre-declared power-integrated fallback), net
  energy = run energy minus (mean power of the preceding rest window)
  x run duration. Per run (PI decision 12): J/token = sum of net joules / sum
  of generated tokens (EOS counted as generated); zero generated tokens
  gives "undefined". Also reported per run and per prompt: gross
  energy, prefill and generated tokens, stop reasons, J per
  (prompt + generated) token.
* **Reading:** the adapter / base J/token ratio depends on how many
  tokens each arm generates (prefill amortisation, EOS) and on the text
  produced; it is a descriptive figure of this demo, not a measure of
  the intrinsic cost of LoRA.
* **Rest guard:** the NH-81 GB300 rule (exclusivity check before
  probes, T = k x P_rest, same k as the NH-81 prereg) with P0 / P_rest
  / P_load measured again for this process (35B model loaded,
  stabilisation load = unmeasured `base` runs). A run is rejected and
  replayed if a rest window exceeds T, a process outside the allowed
  list appears on the GPU, or the NH-81 GB300 CPU rule fails.
* **Statistics:** none inferential. Per domain and arm: median and
  range over the valid runs; per domain the ratio of the adapter and
  base medians of J/token is listed. No CI, no test, no claim of
  difference.

## 5. Runtime

* MLX `0.31.1` with `mlx-cuda-12==0.31.1` (fallback `mlx-cuda-13`, as
  in NH-81 PI decision 4) and `mlx-lm==0.31.2` (PI decision 3). Checked in the
  `mlx-lm` 0.31.2 wheel (SHA-256
  `a90a7905031b2580b4923f92e0fb156ca287f452bb1a9e41a60dcbc971532d46`,
  read only): `models/qwen3_5_moe.py` loads the Hugging Face BF16
  checkpoint and splits the fused `mlp.experts.gate_up_proj` into
  `switch_mlp.{gate,up}_proj`, with keys renamed to
  `language_model.model.layers.N...`, the naming used by the adapters;
  `tuner/utils.py` wraps `SwitchLinear` in `LoRASwitchLinear`;
  `models/gated_delta.py` uses a Metal kernel on Apple GPUs and a pure
  `mlx` ops path otherwise (expected on CUDA; slower, not measured).
* `mlx-lm` 0.31.2 requires `transformers>=5.0.0`, `sentencepiece`,
  `protobuf`, `pyyaml`, `jinja2`, `numpy`: all go through the HITL
  package review (section 8). No lockfile before that review.
* Memory: about 72 GB for the BF16 instance plus about 4.1 GB per
  float32 adapter; the transient peak of loading and sanitizing
  (splitting `gate_up_proj`) is not known. The NH-81 6 GB cap does not
  apply here; the 230 GB cap of PI decision 13 does; peak memory per
  prompt is logged. The MLX CUDA allocator's
  placement on this coherent CPU-GPU system, CUDA on `sm_103` and the
  64 KB page size are not verified; peak memory is logged.

  adapter blocks, `summary.json`. Instrument, guards and rules come

  prompt checks, K calibration, adapter check, J/token, summary.

## 9. Output format

`results/` of the demo working directory:

* `host.txt` (nvidia-smi, kernel, page size, packages, processes),
  `smoke.txt`, `rest_threshold.json` (GPU identity, instrument, P0,
  P_rest, P_load, k, T, discriminative flag, model load time).
* `runs.jsonl`, one line per measured run: `domain`, `arm`
  (`base` / `adapter`), `attempt`, `k_repeats`, `t0`, `t1`, `dur_s`,
  `gpu_j` (gross), `rest_power_w`, `j_per_token`, `j_per_token_gross`,
  `generated_tokens`, `prompt_tokens`, `stop_reasons`, `valid`, `short`,
  `layout`, the GB300 window fields (`instrument`, `rest_max_w`,
  `load1`, `host_foreign_cores`, `cap_w`, `cap_changed`,
  `instrument_invalid`, `foreign_gpu_pids`, `busy_python`, other GPUs),
  and the rest windows before and after.
* `outputs.jsonl`: `domain`, `arm`, `attempt`, `prompt_id`,
  `rendered_ids_sha256`, `prompt_tokens`, `generated_tokens`, `finish`,
  `text`, `text_sha256` (published, PI decision 7).
* `summary.json` (per (domain, arm) medians and ranges, exclusions,
  short runs, ratio of medians; status "demo, not a scientific claim")
  and the note `docs/results/2026-11-01-demo-35b-gb300.md`, which
  starts with "Demo, not a scientific claim".
