# NH-81 amendment 1 (2026-10-28)

Amends `2026-10-25-nh81-joules-per-token.md` (tag `prereg-nh81-20261025`).

**Timing.** This amendment was written on 2026-10-28, **after** the
measurement of 2026-10-25 (first pair 21:28 CET, last window 22:27 CET)
and after the results were known. It records deviations from the frozen
protocol. It changes no threshold, workload, statistic, rejection rule or
estimate of R; it does change the **label** of the verdict (A1).

## A1. Instrument: IOReport GPU rail is the final instrument on macM1

Preregistered (section 5): `powermetrics` (PI-run under sudo) primary,
IOReport "Energy Model" as the alternate; if the powermetrics log is
absent, the verdict is labelled **"provisional (IOReport)"** until a
powermetrics replication by the PI.

What happened, in order:

* 2026-10-25 19:04 CET, before the freeze (tag at 19:31) and before any
  measurement, the PI stated that `powermetrics` would not be reliable
  with OrbStack and the VM `srv` running. The preregistration took this
  into account by making the GPU rail the primary metric and CPU/package
  descriptive only, but it still kept `powermetrics` as the primary
  instrument and the "provisional" label.
* The run of 2026-10-25 was made without a powermetrics log
  (`measure.jsonl`, `start` record: `"powermetrics_log": false`), so the
  analysis produced `"instrument": "IOReport (provisional)"` in
  `results/nh81/summary.json`. That generated file is left unchanged.
* 2026-10-28, after the measurement, the PI decided that the macM1
  verdict rests on the GPU rail read through IOReport, without a
  powermetrics replication: sudo is not available to the agent, and the
  PI's pre-measurement assessment of `powermetrics` under OrbStack stands.
  IOReport reads the same hardware counters for the GPU rail (channel
  `GPU Energy`, cumulative, nJ).

Consequence. Under the frozen protocol alone, the macM1 verdict reads
**"withdraw, provisional (IOReport)"**. With this post-measurement
amendment, the provisional label is lifted. Readers who reject
post-measurement amendments should keep the provisional reading; the
decision (withdraw) and the numbers are the same under both readings. No
GPU-rail cross-check against `powermetrics` exists. The independent
confirmation remains the NVML measurement on the KXKM RTX 4090 (section 8
of the prereg).

## A2. CPU energy not usable

The IOReport CPU channel (`CPU Energy`) did not update reliably: `cpu_j`
is 0 in 146 of the 148 rest/run windows and jumps in two isolated windows
(`measure.jsonl` line 39, W1 fused pair 9 spiking run, 6728 J in 35 s;
line 115, W1 event rest before pair 10, 1041 J in 20 s), i.e. stale
counters released in bulk. No CPU descriptive is reported. The
preregistration already made CPU/package descriptive only.

The same two windows carry the only non-zero ANE values (1.03 J and
0.036 J). The ANE is added to the GPU rail as preregistered; dropping it
moves the primary R-hat from 0.9095 to 0.9098. The GPU channel itself
shows no carry-over: the rest windows that immediately follow runs read
0-0.3 J over 20 s, against 237-1569 J per run.

Already declared in the prereg (section 2): training on the macM1 GPU
instead of electron-server. For completeness: the spiking arm's training
started at about 19:30 CET, one to two minutes before the freeze commit
(19:31:17); at the freeze, only the step-250 evaluation existed. The dense

## A5. Code change after the measurement

Review on 2026-10-28 found that a failed GPU-utilisation read (`-1`) would
have passed the start guard and the rest-window rejection rule. Both now
fail closed (`measure.py`, `analyze.py`). No window of the run has a
failed read; re-running `analyze.py stats` on the raw log reproduces
`summary.json` byte for byte.
